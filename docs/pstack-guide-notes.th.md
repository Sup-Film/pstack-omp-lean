## ตอนที่ 1 ว่าด้วย verification

**ใจความหลัก** agent ที่ตรวจงานของตัวเองไม่ได้ จะทำให้คนต้องคอยเฝ้ามันตลอด skill สำหรับ verification จึงสำคัญที่สุด
poteto มองว่ามันเป็นโครงสร้างพื้นฐาน ไม่ใช่ skill ธรรมดา และยกให้เป็นเหตุผลหลักที่เขาส่ง PR ได้หลักพันต่อเดือนโดยคุณภาพไม่ตก

**สร้างอย่างไร**
- pstack มี `/create-verification-skill` ให้ agent สร้าง skill นี้ให้แอปของเรา และมี `/maintain-verification-skill`
  ไว้รันเป็นประจำ เขาแนะนำให้รันวันละครั้ง
- stack ที่มีเครื่องมือ debug ครบ (เช่น Chrome DevTools Protocol สำหรับเว็บและ Electron หรือ simulator ของ iOS)
  ทำให้ agent ควบคุมแอปได้ง่ายกว่า ถ้า stack ไม่มี ก็ให้ agent สร้างเครื่องมือขึ้นเอง
- หลัก "Build the Lever" คือให้เครื่องมือกับ agent ดีกว่าให้แค่ markdown ในทางปฏิบัติคือ CLI เล็กๆ ที่สั่งงานและ debug
  แอปได้ ช่วยประหยัด token และทำให้ผลซ้ำได้
- CLI ที่เป็นมิตรกับ agent ควรประกอบกันได้ง่าย มี `--dry-run` สำหรับคำสั่งที่มีผลข้างเคียง ใช้ subcommand เปิดเผย
  ความสามารถทีละชั้น มีข้อความ error ที่บอกว่าควรทำอะไรต่อ มี `--help` ที่ละเอียด และส่งผลลัพธ์เป็น JSON
- ต้องคิดเรื่อง dev experience ด้วย เช่น seed ฐานข้อมูล, ผู้ใช้ทดสอบ, auth และการเปิด environment ให้เหมือนกันทุกครั้ง

**Feature Map** คือแผนที่ฟีเจอร์ของแอปในรูป markdown ที่ค้นได้ บอกว่าแต่ละฟีเจอร์ทำอะไรและไปถึงได้อย่างไรจากมุมผู้ใช้
`/create-verification-skill` สร้างให้อัตโนมัติ poteto มองว่ามันเป็น "หน่วยความจำที่ถูกบีบอัด" ของ codebase
ซึ่งเป็นแหล่งความจริงที่ดีที่สุดอยู่แล้ว

**ทำงานขนาน** เขาไม่แนะนำ worktree เพราะกินพื้นที่และทรัพยากรเครื่อง แนะนำ cloud agent ที่มีเครื่องจริงของตัวเองแทน
โดย bot ทำหน้าที่ประสานงาน ส่งงานทั้งก้อนให้ cloud agent ที่รัน `/poteto-mode` เอง เพื่อให้ context ของ bot สะอาด

**ตัวอย่างการใช้**
- สร้างฟีเจอร์แล้วให้ verify ด้วย skill ควบคุมแอป พร้อมวิดีโอและภาพหน้าจอเป็นหลักฐาน
- งาน perf ให้วัด trace ก่อน แก้ตรงจุด แล้วใช้ `/swarm` รัน verification หลายรอบเพื่อให้ได้จำนวนตัวอย่างพอยืนยันผล
- ตั้ง routine ให้ bot ฟังรายงานจากผู้ใช้แล้วลอง reproduce อัตโนมัติ

## ตอนที่ 2 ว่าด้วย research, planning และ architecture

**ปัญหาที่ยังเจอแม้โมเดลเก่งขึ้น** มีสองข้อ คือ agent ไม่เข้าใจเจตนาเพราะโจทย์ไม่ชัด และ agent มี context ไม่พอจะทำงานให้ถูก
ทางแก้ของทั้งสองข้อคือเติม context คุณภาพสูงให้ agent ก่อนลงมือ

**ให้ agent พูดด้วยคำของตัวเอง** แทนที่จะบอกคำตอบที่อยากได้ ให้ agent เล่าปัญหาด้วยคำของมันเองก่อน วิธีนี้บังคับให้มัน
สรุปเรื่องที่วุ่นวายเป็นโจทย์ที่ชัด ทำให้เราจับความเข้าใจผิดได้ก่อนเขียนโค้ด และไม่ชี้นำมันไปตามสมมติฐานของเราซึ่งอาจผิด

**สร้าง mental model**
- `/teach` ให้ agent อธิบายสิ่งที่ทำให้คนเข้าใจ เบื้องหลังเรียก `/how` และ `/why`
- `/how` ไล่กลไกขณะรันจริง ถ้า subsystem ข้ามหลาย directory หรือหลาย service จะ spawn explorer ขนานบนโมเดลที่เร็วและถูก
- `/why` ค้นเหตุผลเบื้องหลังจากหลายแหล่งพร้อมกัน เช่น ประวัติ git, comment ใน PR, ticket, เอกสารออกแบบ, แชท และ monitor
- poteto สังเกตว่า agent มักพูดอย่างมั่นใจทั้งที่ไม่ได้อ่านโค้ดจริง การให้มันอธิบายจึงช่วยตัว agent เองด้วย
- `/recall` ดึง context จากบทสนทนาเก่า เพราะงานหลายงานกินเวลาหลาย session

**วางแผนด้วยโค้ด** poteto บอกว่า plan mode ของ harness ส่วนใหญ่ลงรายละเอียดการ implement มากเกินและอธิบายเรื่องอื่นน้อยเกิน
เขาจึงวางแผนผ่านโค้ด
- สำหรับโค้ดที่คนอื่นจะใช้ เขาเขียน README หรือ tutorial ก่อน แล้วย้อนกลับไปหา API และสถาปัตยกรรม
- `/technical-writing` แยกเอกสารตามกรอบ Diátaxis เป็น tutorial, how-to, reference และ explanation และใช้ `/unslop`
  ให้อ่านง่าย
- แผนแบบนี้ให้เป้าที่ agent ใช้ตรวจงานตัวเองได้

**ความผิดพลาดที่พบบ่อยตอนวางแผน** คือรับแบบแรกที่ agent เสนอ และปรุงแผนนานเกินไปโดยไม่มีหลักฐานเชิงประจักษ์
- playbook prototype ให้ agent ลองหลายแบบขนานกัน ใส่ตัวสลับ วัดผล และถ่ายภาพหน้าจอ เพื่อตอบคำถามด้วยหลักฐานแทนการรอคน
- `/architect` แบ่งงานออกแบบเป็นขั้น คือ ปูพื้นด้วย `/how` และ `/why`, ใช้ arena ให้ runner อิสระหลายตัว (มักต่างตระกูลโมเดล)
  ร่างแบบเป็น type และ signature, ให้ cross-judge ที่ใช้โมเดลต่างจาก agent หลักให้คะแนน, implement ตาม sketch และทิ้งแบบ
  เมื่อมีหลักฐานว่าผิด เช่น workaround เดียวกันโผล่หลายที่ หรือ type ต้องใช้ `any` หรือ cast
- เขาไม่ทำ adversarial review กับแผนที่ยังเป็นนามธรรม เพราะ agent มักคิดความเสี่ยงที่ไม่มีจริงขึ้นมาเอง

**ถ้าอยากได้เอกสารแผนจริงๆ** playbook multi-phase plan ใช้หลังได้แบบที่พอใจแล้ว ทุกงานในแผนต้องมีการพิสูจน์ว่าทำงานจริง
เทสต์อย่างเดียวไม่พอ แผนถูกตรวจโครงสร้างด้วย script และแต่ละ PR เล็กพอจะ review ได้ เขาเก็บแผนไว้ใน codebase ชั่วคราวเท่านั้น

**ตัวอย่าง prompt ในบทความ** ครอบคลุมการสืบบั๊กที่ยังไม่รู้สาเหตุ, การออกแบบขอบเขต service ใหม่ด้วย `/architect`
พร้อม prototype, การ migrate หลาย PR และการแก้ปัญหาจาก Slack ด้วยการ reproduce ก่อนแล้วแนบวิดีโอเป็นหลักฐาน

## เทียบกับ repo นี้

| แนวคิดจากคู่มือ | repo นี้ |
|---|---|
| agent ต้อง verify งานตัวเองด้วยการรันจริง | agent หลักเขียนโค้ดและรัน verification เอง Feature และ Bug fix ต้องแนบผลการรันในคำตอบ |
| Build the Lever | การเฝ้า CI เป็น shell job งาน refactor แบบกลไกใช้ codemod แทน subagent |
| `/swarm` เพื่อจำนวนตัวอย่าง | คงเดิม |
| prototype หลายแบบขนาน | คงเดิม |
| `/architect` ใช้ arena และ cross-judge | คงเดิม ทุกครั้งที่เรียก architect |
| `/how` spawn explorer เมื่อข้ามหลาย directory | spawn `scout` เมื่อคำตอบข้ามตั้งแต่ 3 directory หรือ 2 service แต่ agent หลักเป็นคนเขียนคำอธิบาย |
| agent พูดมั่นใจโดยไม่อ่านโค้ด | เป็นเหตุผลที่ให้ agent หลักอ่านและอธิบายเอง แทนการรับสรุปจาก subagent |
| `/why` ค้นหลายแหล่งขนาน | agent หลักค้น git เอง ใช้ investigator ขนานเฉพาะแหล่งที่ไม่ใช่ git |
| ไม่ review แผนนามธรรม | ไม่ได้เพิ่ม plan review |
| multi-phase plan ตรวจด้วย script | คงเดิม |
| cloud agent แทน worktree | OMP บนเครื่องไม่มี cloud agent งานขนานยังใช้ worktree |
| runner และ judge ต่างตระกูลโมเดล | ขึ้นกับ config ถ้าทุก role เป็นตระกูลเดียวกัน จะได้แค่ context ที่อิสระ |

รายละเอียดของแต่ละการตัดสินใจอยู่ใน [`single-loop/decisions.tsv`](single-loop/decisions.tsv)
